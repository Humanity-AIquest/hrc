01 What Phase 1 actually is

Phase 1 is not an open-source development community. There is no code contribution, no sprint board, no pull requests. Phase 1 is:

  • People join and are vouched in as verified humans.
  • They deliberate on the 52 clauses — argue, amend, translate, object.
  • They ratify version 1 of the Humanities-AI Rights Constitution.
  • Their own agent helps them do all of it.

The deliverable is a membership, a ratified constitution, and a proof of concept credible enough to raise against.

The reframe that keeps the IP thesis alive with no code. In Phase 1 the contribution ledger records constitutional contributions — clause drafts, arguments, translations, votes, objections. Same provenance, same hash chain, same attribution to a verified human.

The ledger gets built and proven on deliberation before a single line of code exists. And "we ratified a constitution through agent-assisted deliberation, with every contribution attributed to a named human" is a stronger thing to show an investor than a half-built project tracker.

Everything to do with software delivery — GitHub App, constitutional CI, work assignment, PR review — is Phase 2, and is listed in §09 so it is not lost.

02 Decisions now locked

D1

Verification is vouching, seeded by GitHub history. Existing verified members vouch for newcomers, staking their own standing. No ID scanning.

Identity documents inside a digital-rights project is an irony critics would never drop, and it excludes precisely the people the constitution claims to serve. Vouching also builds the social graph the platform needs later.

D2

Token cost is hybrid. Platform funds a monthly allowance for governance work. Code work in Phase 2 is bring-your-own-key.

Constitutional participation must never be paywalled. Heavy compute can be, because by then the participant is a developer with their own key.

D3

No blockchain. Signed, hash-chained records in D1, with published chain roots.

Delivers the property actually needed — tamper-evidence — without wallets, gas, key-loss support burden, or securities exposure. Revisit only if federation demands cross-instance trustlessness.

D4

Agents cannot touch members until registered. An agent reaches a human only after its human has accepted the Constitution and holds an active scope. Acceptance is the firewall.

This is the security model stated as a constitutional act rather than a technical one, which is the correct framing for this project.

D5

Solo build, lean. Maximum reuse of the existing SPA, D1 schema, auth, clause explorer, chat agent, and admin dashboard.

Scope is cut to what one person can ship and defend. See §08.

What the plugin carries

A plugin is a versioned bundle of agent configuration distributed as a git repo, installed from a marketplace. It can hold an MCP server config, skills, subagents, slash commands, and hooks. For Phase 1:

  • MCP config — the connection to mcp.humanity-ai.quest
  • Bootstrap skill — roughly twenty lines: fetch your working instructions from hrc://protocol
  • Commands — /hrc, /my-positions, /draft-amendment, /where-do-i-stand
  • Subagents — a clause analyst, and a devil's advocate whose job is to argue against the member's own position

That devil's advocate is not a novelty. Institutionalised dissent is the honest answer to the charge that agent-assisted deliberation manufactures consensus.

04 Thin plugin, thick server

Anything baked into the plugin is invisible to staff and unrevokable once distributed. Anything served by the MCP server is visible and controllable in real time.

Members cannot be forced to update. If clause text or conduct rules live inside the bundle, in six months there are eleven versions in the wild, all behaving differently, with no way to see or fix it.

In the plugin

Static · rare updates
  • Server URL and OAuth config
  • Command names and shapes
  • Bootstrap skill — a pointer, not content
  • Subagent shells

Served by MCP

Live · fully controlled
  • All 52 clause texts and amendments
  • The deliberation protocol
  • Agent conduct rules
  • Constitutional check logic
  • Anything that could ever need revoking

Plugin versions then change only when the shape changes, never when the content does. Content changes are instant, audited, and revertible in one click.

The version handshake

Every connection reports client type, client version, and plugin version. The server records it, which is what makes the admin dashboard an instrument rather than a guess. It enables: live adoption data, warnings on outdated versions, refusal below a minimum version, and version-appropriate responses during a migration.

06 Trust & attribution

Authentication

OAuth 2.1 with PKCE, protected-resource metadata per RFC 9728, scope-bound tokens encoding the tool subset they may invoke. The MCP server is a resource server only — it validates, never issues. Under a tenth of public MCP servers use OAuth at all; over half still rely on static API keys. Doing this properly is both correct and a claim worth making out loud.

Assume every connecting client is hostile. The agent may be any model, jailbroken, or adversarial. Authorization, attribution, rate limits, and constitutional checks are therefore server-side without exception. The client never asserts identity; it presents a token.

Attribution

Modelled on the Developer Certificate of Origin rather than a CLA — a lightweight per-contribution assertion signed at the moment of contribution, not a legal document signed once up front. That low barrier is the point, and it is why Chef and GitLab both migrated. Two fields are added that the DCO lacks:

  • AI disclosure — which model, what role (drafted / assisted / reviewed), how much. Declared, not inferred.
  • Constitutional verdict — the hrc_check result at the moment of sealing, stored with the entry.

Entries are hash-chained and chain roots are published, so a rewrite is detectable by anyone. That is the property actually required, and it needs no chain.

Standing constraint

A member's agent is only theirs if we cannot read it. Telemetry stops at metadata and safety-classifier verdicts — never stored prompt content. Building surveillance inside a digital-rights platform is the first thing a critic reaches for, and they would be right.

07 Admin: versions, approvals, visibility

The organising principle is that staff approve and configure; they do not fill in forms an agent could have filled in. Two release streams, deliberately separate.

Stream 1 — Plugin releases

Staged promotion, human click required between each stage. Nothing reaches members automatically.

Draft

Built, not distributed. Visible to staff only.

Staged

Installable by staff accounts for verification.

Canary

Opt-in cohort. Error rate and adoption watched.

General

Offered to all members. Rollback available.

Each stage records what changed, who promoted it, how many clients are running it, and the error rate since promotion.

Stream 2 — Content changes

Clause text, protocol, conduct rules, prompts. These go live the instant they are approved, which is exactly why approval happens before publish. Diff view, named approver, stated reason, one-click revert to any prior version.

Because content is server-side, a bad publish is reverted in seconds. Because plugin releases are staged, a bad release never reaches everyone at once. Those two properties are the entire reason for keeping the streams apart.

/admin/releases

Release pipeline

  • Promote through draft → staged → canary → general
  • Changelog, approver, timestamp per stage
  • Live adoption by plugin version
  • Rollback and minimum-version enforcement
/admin/content

Content approvals

  • Pending changes to clauses, protocol, conduct
  • Side-by-side diff before publish
  • Approve, reject with reason, or revert
  • Full version history, every change attributed
/admin/clients

Connected clients

  • Who is on which client and which version
  • Deprecation windows and sunset dates
  • Broadcast notices to connected agents
  • Refuse connections below a minimum
/admin/tools

Tool registry

  • Enable, deprecate, or retire per tool — no redeploy
  • Schema version and diff
  • Call volume, error rate, p95 latency
  • Rate limits by role
/admin/scopes

Scopes & mandates

  • Scope definitions mapped to tools
  • Which roles may hold which scopes
  • Mandates expire by default
  • Emergency revocation, per member or global
/admin/approvals

Action inbox

  • Agent actions awaiting human approval
  • Reasoning, constitutional verdict, cost
  • Approve · redirect · reject with reason
  • Rejection reasons feed prompt improvement
/admin/members

Membership & vouching

  • Vouch graph and chains of trust
  • Pending verifications
  • Standing, and revocation cascades
  • Allowance usage per member
/admin/ledger

Contribution ledger

  • Every sealed contribution, with AI disclosure
  • Chain integrity check and published roots
  • Platform agents public, member agents private
  • Export for audit
/admin/constitution

Ratification progress

  • Consensus per clause, contested clauses first
  • Road to V1 — clauses above threshold
  • hrc_check pass rate — 100% means the checks are toothless
  • Amendment impact preview

Changes to versions, tools, scopes, and content are themselves logged as admin actions, under the same audit trail as everything else.

08 Build order for one person

Sequenced so there is something demonstrable at every stage, and so nothing can write to state before identity and transport are proven.

P0 · 2wk

Read-only server

whoami, hrc_lookup, resources, OAuth end to end. Zero write paths. Reuses the existing clause data and auth.

P1 · 1wk

Plugin v0.1

Marketplace repo, bootstrap skill, /hrc. First external member connects their own agent. This is the demo that raises money.

P2 · 2wk

Deliberation tools

submit_argument, draft_amendment, cast_vote, hrc_check. Real constitutional work now flows through the protocol.

P3 · 2wk

Vouching & ledger

vouch_for, record_contribution, hash chain, AI disclosure. Provenance becomes real.

P4 · 2wk

Admin release & approvals

/admin/releases and /admin/content first — the two screens without which everything above is invisible to staff. Then clients, tools, scopes.

Roughly nine weeks solo to a POC that demonstrates the entire thesis. Cut P4 down to the two priority screens if time is short; do not cut them entirely.

09 Explicitly deferred to Phase 2

Recorded so it is not relitigated, and so investors can see the roadmap is deliberate rather than unfinished.

  • GitHub App, work assignment, PR review, constitutional CI as a required status check
  • The AI-contribution wedge — provenanced agent PRs in a landscape where most projects are banning them
  • Clause↔code traceability and amendment impact analysis across a codebase
  • Hosted or containerised member agents, and any code execution on our infrastructure
  • The agent workforce — triage, QA, docs, release agents
  • Value distribution beyond attribution
  • Federation to other communities

10 Still open

  • Vouch mechanics. How many vouches admit a member? Does a revoked voucher cascade to those they admitted? What stops a vouching ring? Needs a written rule before P3.
  • Allowance size. What monthly token budget makes governance participation genuinely free without becoming the largest line item pre-funding?
  • Ratification threshold. What consensus level ratifies a clause into V1, and who certifies it? This is a constitutional question, not a product one — and it should be decided by the members, in public, which is itself a good demonstration.
